How Cloud Sync Works

One document, kept in step across a person's Macs. A shared library and server do the moving; each app decides what its document means. Shorty is the first app on it, and Swurl is next.

Two words to keep apart

Sync moves the document between Macs, through the server. It only ever changes a file.

Apply makes one Mac match its file. Only the app knows how. Shorty writes keyboard settings; syncing alone never does.

The pieces

Every Mac runs the same library. The library calls one interface, SyncHost, for anything that depends on the app. The server stores revisions of a document it never reads.

One edit, from Mac A to Mac B

Revisions form one straight line, numbered from 1. Each write says which revision it was based on, so the server can refuse a write made from out-of-date text.

When two Macs write at once

Say Mac B pushes with If-Match: 7 after the server has reached 8. The server answers 409 with revision 8 attached. Mac B merges, saves the merged file, and pushes again on top of 8. It tries up to four times. If the merge leaves nothing new to send, it stops there. A merge that can't produce a valid document takes the server's version whole and backs the local file up first.

Linking another Mac

A Mac joins by showing a code that a Mac already linked approves. No password exists anywhere in this flow. The first Mac creates the account with an invite instead.

One server for every app

One deployment serves every app and every Mac. An account is shared across apps, and each app gets its own namespace inside it: a short name in the request path, such as /v1/ns/swurl/doc. A namespace holds that app's document, revisions and live connections, and it exists once something is written to it, so a new app needs no server change.

The same Worker runs in two places, and one set of tests holds both to the same behaviour. On Cloudflare it's a Worker, D1 and Durable Objects, which works on the free plan for a handful of Macs. Self-hosted it runs under celld, Deno's open-source Workers runtime, as one Docker container with its state in a volume. It needs HTTPS in front of it unless it's on localhost, and it has no rate limit on starting a pairing.

Because every app shares the deployment, one outage or bad deploy stops sync for all of them.

The same engine, two apps

Both apps sync one text file. They differ in what a change means, which is why merging belongs to the app.

Built, running on the dev server

Shorty

Use case: you rebind Pin Tab on your MacBook. Your Mac mini gets the new shortcut without you doing anything there.

The document is a set of keyed entries, one per app and menu title. Two Macs that edit different entries never conflict.

Last synced
com.google.Chrome:
  "Pin Tab": cmd+p
Mac A changes
com.google.Chrome:
  "Pin Tab": cmd+shift+p
Mac B adds
com.google.Chrome:
  "Pin Tab": cmd+p
  "New Tab Below": cmd+opt+t
Merged: both kept
com.google.Chrome:
  "New Tab Below": cmd+opt+t
  "Pin Tab": cmd+shift+p

If both Macs change the same entry, this Mac's value wins, except that an edit beats a delete. After saving, the app applies the file, or waits if Apply Changes Automatically is off.

Proposed, not designed yet

Swurl

Use case: you add a rule at work so docs links open in your Work profile. Your laptop at home routes those links the same way.

The document is an ordered list: the first match wins, so where a rule sits is part of its meaning. The file also keeps your comments.

Last synced
rules:
  # Client work first
  - name: Docs
    open: work
  - name: Video
    open: home
Mac A inserts above
rules:
  # Client work first
  - name: Client
    open: client
  - name: Docs
    open: work
  - name: Video
    open: home
Mac B moves Video up
rules:
  - name: Video
    open: home
  # Client work first
  - name: Docs
    open: work
Merged: needs a design
rules:
  Client or Video first?
  Where does the comment go?

Keyed merging can't answer this, so Swurl supplies its own merge. A rule name is optional, so a rule has no reliable identity yet either.

When something is wrong

Sync never guesses when it can wait. Each state below shows in the app, and only the first retries by itself.

StateWhat happenedWhat sync does
OfflineThe connection droppedRetries after 1 s, 2, 4 and so on, up to 5 minutes, sooner on wake or a network change
Waiting for a valid fileThe file can't be read, or has errorsSends nothing and holds remote changes until the next edit fixes it
File movedThe app now uses a different file than the one linkedStops until the person pulls, or force-pushes that file
RemovedAnother Mac revoked this oneStops. The file stays as it is
Update neededThis build is below the server's minimum, or the document is newer than it can readStops and asks for an update

Any revision can be restored. Restoring adds a new revision with the old text, so nothing in the history is lost. Each app's document keeps its latest 1,000 revisions.
